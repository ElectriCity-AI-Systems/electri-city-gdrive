# ElectriDrive 2.1.3 — QA safety acceptance, 2026-10-30

## Starting point and result

The working tree began clean at `50f00e26ee0b3e9dfe0920316dc72f4b1d59d9c0`
on `codex/electridrive-test-20261009-final`, with 278 passing tests. PR #20
already targets main and remains a draft. Isolating XDG settings alone did not
restrict which source a user could select.

The explicit QA policy now seals a private profile to an empty synthetic local
root, keeps activation persistent, validates settings at startup and execution,
and refuses relative/traversal/symlink/hardlink escapes. Both engines, configured
runner, GUI Sync now/all, queued workers, manual transfers, retries and CLI share
these guards. Regular mode retains ordinary paths, OAuth and SQLite behavior.

Cloud targets require registered immutable IDs, profile nonce, exact name and
parent metadata. Only an explicitly invoked command creates a new artificial
root; existing names cannot enroll a target. Fresh ancestry checks prevent use
of stale/reparented selections. Deletion, raw API access, account-wide listings,
Changes API, Picker and FUSE are unavailable in QA. Isolated OAuth remains usable
without importing ordinary credentials, keyring entries or settings. The window
title, permanent banner and setup instructions clearly identify QA mode.

A new empty persistent `qa-safe-profile` and disjoint `qa-safe-data` were created
beside the source checkout. Their startup check confirms zero pairs and zero
cloud roots. No OAuth files were copied or read. A metadata/settings-only check
found that the older `qa-connected` profile still contained one pair; it was left
unchanged rather than automatically sealed or cleaned. The ordinary installation
and its personal pairs were not opened or changed.

## Review corrections

Independent review found and reproduced four issues during development: symlink
log append, SQLite pathname escape, a moved download parent, and permissive
normalization of malformed settings. All were fixed with regression tests.
QA uses secure append descriptors and atomic file operations; its database is
in memory with a parameterized, private JSON snapshot and an exclusive process
lock. SQLite never opens a QA legacy database filename or sidecar. A subsequent
review found a lock-directory ancestor race; component-by-component no-follow
opening fixed it, with a failing-before/passing-after regression. The final scoped
independent check passed 41 safety/database tests and confirmed this last fix.

Review also corrected rejected Full Drive changes mutating live settings and
missing restart instructions after external root registration. Unsupported UI
choices are disabled, scope rejection preserves settings/credentials, and setup
text describes only QA-supported actions.

## Limits and operation

See [QA design and usage](QA-SAFETY-DESIGN.md). This is application policy, not a
kernel sandbox against a hostile process running as the same user. Concurrent
namespace races after the last descriptor identity check and Drive reparenting
between metadata validation and mutation cannot be made atomic by this policy.
Deliberate personal copies inside declared synthetic roots are not identifiable
as artificial data. Cloud capabilities start empty; first-root creation is a
separate explicit cloud-writing action with GUI closed, followed by restart.
Only one process may own a QA state database at a time. Existing ordinary SQLite
state is never imported automatically. The new profile needs its own explicit
OAuth setup; no live authorization was attempted.
